# 企业级 AI 智能体平台验收测试手册

## 1. 验收目标

验证以下最小闭环是否可用：

1. 前端可以访问并通过 Vite 代理调用后端。
2. Markdown 文档可以入库、按标题切分并查询处理状态。
3. 问答会先执行租户和用户权限过滤，再返回答案与证据。
4. 证据不足时系统拒答，不生成无依据答案。
5. 开启人工审批后，问答会停在 `WAITING_APPROVAL`，审批通过后继续执行。
6. 关系图谱、评测入口和健康检查可以返回结果。

## 2. 当前验证结论

| 检查项 | 结果 | 证据与边界 |
| --- | --- | --- |
| Java 编译与单元测试 | 通过 | `rtk mvn -q test` 退出码为 0 |
| 后端打包 | 通过 | `rtk mvn -q package` 退出码为 0 |
| 前端生产构建 | 通过 | `vite.cmd build` 生成 `frontend/dist` |
| Compose 静态配置 | 通过 | `docker compose --env-file .env.example config --quiet` |
| local profile 外部依赖 | 未启用 | local 使用内存实现，不需要 PostgreSQL、Redis、RabbitMQ、Neo4j |
| Docker 外部服务真实联调 | 未验证 | 本次没有启动 Docker Compose |
| 浏览器点击链路 | 待现场执行 | 需要后端和前端同时启动后按第 4 节操作 |

因此，当前可以提交为“local profile 的可运行最小闭环”；不能把当前证据表述为“RabbitMQ、Neo4j、ParadeDB 已完成真实生产联调”。

## 3. 启动方式

后端终端：

```powershell
rtk powershell -Command "mvn spring-boot:run -Dspring-boot.run.profiles=local"
```

前端终端：

```powershell
Set-Location frontend
rtk powershell -Command "npm.cmd run dev"
```

浏览器访问：`http://localhost:5173/`

启动后先检查：

```powershell
Invoke-RestMethod http://localhost:8080/actuator/health
Invoke-WebRequest http://localhost:5173/ -UseBasicParsing | Select-Object StatusCode
```

预期：后端健康状态为 `UP`，前端 HTTP 状态为 `200`。

## 4. 推荐端到端测试

### 4.1 入库一份测试知识

将 `docs/knowledge-base/01-平台能力说明.md` 的正文提交到页面“知识入库”区域，或者使用以下 PowerShell：

```powershell
$base = 'http://localhost:8080'
$document = @{
  documentId = 'kb-platform-capability-v1'
  tenantId = 'tenant-demo'
  source = '平台能力说明'
  version = 'v1'
  permissionTags = @('public')
  allowedUserIds = @()
  markdown = @'
# 企业级 AI 智能体平台能力说明

## 文档处理

平台支持 Markdown 文档，按照标题层级切分为 Chunk，并保留标题路径作为上下文。

## 可信问答

平台先执行租户和用户权限过滤，再进行混合检索。证据不足时系统会拒答。
'@
} | ConvertTo-Json -Depth 6

$ingest = Invoke-RestMethod "$base/api/documents/markdown" -Method Post -ContentType 'application/json' -Body $document
$ingest | ConvertTo-Json -Depth 8

$status = Invoke-RestMethod "$base/api/documents/kb-platform-capability-v1/ingestion-status?tenantId=tenant-demo"
$status | ConvertTo-Json -Depth 8
```

预期：`chunkCount` 大于 0，入库状态为 `SUCCESS`。再次提交完全相同的 `documentId`、版本和正文时，状态应体现幂等跳过，即 `SKIPPED`。

### 4.2 验证证据问答

```powershell
$question = @{
  tenantId = 'tenant-demo'
  userId = 'user-demo'
  sessionId = 'session-demo-001'
  question = '平台支持什么文档？'
  requireApproval = $false
} | ConvertTo-Json

$answer = Invoke-RestMethod "$base/api/chat" -Method Post -ContentType 'application/json' -Body $question
$answer | ConvertTo-Json -Depth 10
```

预期：`data.refused` 为 `false`，`data.answer` 不为空，`data.evidence` 至少包含一条证据，且证据中的 `documentId` 为 `kb-platform-capability-v1`。

### 4.3 验证证据不足时拒答

```powershell
$unknown = @{
  tenantId = 'tenant-demo'
  userId = 'user-demo'
  sessionId = 'session-demo-002'
  question = '火星基地的管理员是谁？'
  requireApproval = $false
} | ConvertTo-Json

$refused = Invoke-RestMethod "$base/api/chat" -Method Post -ContentType 'application/json' -Body $unknown
$refused | ConvertTo-Json -Depth 10
```

预期：`data.refused` 为 `true`，`data.refusalReason` 有值，不应出现无依据的管理员姓名。

### 4.4 验证人工审批

```powershell
$approvalQuestion = @{
  tenantId = 'tenant-demo'
  userId = 'user-demo'
  sessionId = 'session-demo-003'
  question = '平台先执行什么，再生成答案？'
  requireApproval = $true
} | ConvertTo-Json

$waiting = Invoke-RestMethod "$base/api/chat" -Method Post -ContentType 'application/json' -Body $approvalQuestion
$waiting | ConvertTo-Json -Depth 10
$workflowId = $waiting.data.workflowId

$checkpoint = Invoke-RestMethod "$base/api/workflows/$workflowId"
$checkpoint | ConvertTo-Json -Depth 10

$approval = @{
  approverId = 'reviewer'
  decision = 'APPROVE'
  comment = '已核对返回证据。'
  version = 0
} | ConvertTo-Json

$completed = Invoke-RestMethod "$base/api/workflows/$workflowId/approval" -Method Post -ContentType 'application/json' -Body $approval
$completed | ConvertTo-Json -Depth 10
```

预期：第一次请求返回 `waitingApproval=true` 和 `workflowId`；检查点状态为 `WAITING_APPROVAL`；通过审批后返回答案或明确拒答，且不再停留在等待审批状态。

### 4.5 验证权限隔离

将 `permissionTags` 设为 `user:alice`，用 `userId=user-bob` 提问同一文档中的专属内容。预期：`data.refused=true` 且 `data.evidence` 为空。再用 `userId=user-alice` 查询，才允许进入后续检索判断。

### 4.6 验证图谱和评测

页面中先点击“查询关系”，再点击“运行最小评测”；或执行：

```powershell
Invoke-RestMethod "$base/api/graph/relations?tenantId=tenant-demo&userId=user-demo&documentId=kb-platform-capability-v1&version=v1&maxHops=3&limit=20" | ConvertTo-Json -Depth 10
Invoke-RestMethod "$base/api/evaluations/run" -Method Post -ContentType 'application/json' -Body '{}' | ConvertTo-Json -Depth 10
```

local profile 下图谱可能显示为本地降级适配器；评测结果用于最小行为回归，不等同于生产 Ragas 指标。

## 5. 失败时的判断顺序

1. 页面打不开：检查前端进程和 `5173` 端口。
2. 页面显示“服务暂不可用”：检查后端 `8080` 端口和 `/actuator/health`。
3. 入库返回 400：检查 `tenantId`、`markdown`、`source`、`version` 是否为空。
4. 问答拒答：先确认文档已 `SUCCESS`，再确认租户、用户、权限标签和问题词汇一致。
5. 审批失败：检查 `workflowId`、审批人 `reviewer`、版本 `0` 和非空审批意见。
6. Docker profile 失败：先执行 Compose 配置检查，再逐项检查 PostgreSQL、Neo4j、RabbitMQ、Redis 的健康状态。
