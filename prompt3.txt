# 企业级 AI 智能体平台：P2 生产化与评测闭环实现任务

你是一名资深 Java / Spring Boot AI 平台工程师。请在**现有仓库**中继续实现 P2 生产化与评测闭环。此任务不是从零搭建项目，也不是重新实现 P0/P1；必须以仓库现状为唯一事实来源增量开发。

## 0. 开始前：核对基线

编码前先阅读并核对以下内容：

- `README.md`、`pom.xml`、`docker-compose.yml`、`.env.example`、数据库初始化脚本。
- `src/main/java/com/agent/document`、`ingestion`、`workflow`、`retrieval`、`api`、`infrastructure`。
- 现有 `src/test` 与 `application*.yml`。

已完成、且不得破坏的基线如下；如果与实际仓库不一致，先报告差异并以仓库为准：

- P0：Markdown 切分与入库、权限预过滤、并行检索/RRF、证据拒答、会话记忆、状态机、评测接口、TraceId 与 Prometheus 指标。
- P1：父子 Chunk 索引和父上下文；受限本地/Neo4j 图关系；内容哈希、版本事件和幂等入库；RabbitMQ 有限重试/死信；ParadeDB 适配及降级；`WAITING_APPROVAL` 审批检查点、审批/恢复 API 和指标。
- `mvn -q test`、`mvn -q package` 已通过；P1 的 local profile/HTTP 行为已验证。
- RabbitMQ、Neo4j、ParadeDB 的代码、SQL、Compose 和降级契约已准备，但尚未完成真实 Docker 容器联调；审批检查点目前仍是内存实现。

保持已有 Markdown 入库与聊天 API 的请求/响应兼容。除非确有兼容迁移方案，否则禁止修改已有路径、字段语义和 local profile 的无外部依赖启动能力。

### 0.1 P1 审计发现的未完成事项：P2 开始前必须收尾

当前仓库虽然已经具备 P1 的主要代码、local 降级实现和单元测试，但以下事项不能直接视为完成，必须先处理或明确记录为未验证：

1. **外部服务尚未真实联调**：Neo4j、RabbitMQ、ParadeDB/PostgreSQL 当前只有适配器、SQL、Compose 和降级契约，尚未证明真实容器中的关系写入/受限查询、消息消费/重试/死信、BM25 建索引/查询和失败恢复。没有启动并验证容器时，不得在 README、界面或最终汇报中写成“已完成真实集成”。
2. **聊天链路缺少图谱参与状态**：当前图谱关系可以通过独立接口查询，但普通聊天链路使用向量/全文检索，不能暗示已经使用 Neo4j 或完成 GraphRAG。为保持 API 兼容，应在聊天响应中增补一个可选的图谱参与状态，例如 `graphEvidenceUsed` 或等价结构；未调用图谱时明确返回 `false`，只有图谱证据实际进入回答上下文时才返回 `true`。本轮不得为了补字段而擅自把普通问答改造成 GraphRAG。
3. **P1 的真实验证边界必须可复现**：补齐或核对 local HTTP、Compose 静态配置、Docker 健康检查、Neo4j 图关系、RabbitMQ 增量入库和 ParadeDB 检索的验证命令，并逐项记录退出码、关键响应和未完成原因。Mock、内存适配器或配置文件只能证明代码契约，不能替代外部服务联调。
4. **P1 文档和测试不能过度声称**：README、验收手册和最终报告必须区分“代码/配置完成”“local 已验证”“Compose 静态验证”和“Docker 外部服务已真实验证”。已有 P0/P1 测试必须继续通过；新增验证不得删除或绕过权限、租户、版本和证据校验。
5. **审批持久化属于本轮 P2 的明确未完成项**：当前审批检查点仍是内存实现，应用重启后不能恢复。P2-A 必须补 PostgreSQL 持久化、版本并发控制、过期/越权/重复审批处理和重启恢复测试；local profile 仍保留内存实现。

只有完成上述 P1 收尾，或在交付报告中明确标记其未验证边界后，才能继续判断 P2 的完成情况。除非用户另行提出 GraphRAG 需求，本轮只要求如实标记图谱是否参与，不要求把图谱强行接入普通问答。

## 1. 本轮 P2 目标

完成以下四项可验证能力：

1. **审批和关键任务状态持久化**：可在应用重启后恢复待审批/已处理状态。
2. **版本化评测与 Bad Case 回归闭环**：可管理数据集、运行评测、沉淀失败样例和重复执行回归。
3. **指标版本化与 Grafana 展示**：能够按合理标签观察检索、入库、审批与评测趋势。
4. **Docker 真实集成验证**：在可用环境中实际启动并验证 PostgreSQL/pgvector、Redis、RabbitMQ、Neo4j、ParadeDB；若环境限制导致无法执行，明确报告证据边界，不得声称完成联调。

不要为了“功能齐全”生成不可运行的空接口。每一项都必须有领域模型、接口、实现、配置、测试和 README 说明。

## 3. P2-A：审批、入库任务与评测运行的持久化

### 3.1 持久化边界与迁移

- 为审批检查点、入库任务状态、评测数据集、评测运行和 Bad Case 定义清晰的持久化端口与领域模型。
- docker/生产 profile 使用 PostgreSQL 持久化实现；local profile 保留确定性的内存实现，确保现有测试和演示仍能运行。
- 采用仓库已有的迁移机制；若不存在，选择一种与 Spring Boot/Maven 兼容的迁移方案，并添加可重复执行、可回滚说明清楚的迁移脚本。禁止依赖手工修改表结构。
- 所有表必须具备主键、`tenant_id`、创建/更新时间、乐观锁或等效并发控制字段；对查询路径增加必要索引。
- 任务/审批状态的更新必须使用条件更新或版本号避免并发覆盖；重复消息、重复审批和重复运行请求应返回幂等结果或明确冲突，而非产生重复数据。

### 3.2 审批恢复

- 将 `WAITING_APPROVAL` 检查点持久化为可重启恢复的记录；保留 workflowId、租户、发起用户、当前状态、待审批动作摘要、过期时间、traceId、版本号和审计信息。
- 恢复 API 必须由持久化状态驱动；重复、过期、越权审批要有稳定的错误码与审计记录。
- 应用启动后能够发现未过期的待审批记录；不得自动批准或自动执行敏感动作。
- 审批意见如需保留，必须设置长度限制、敏感字段脱敏策略和审计访问权限。

## 4. P2-B：版本化评测与 Bad Case 回归

### 4.1 评测数据集与运行

- 实现版本化数据集模型：数据集、版本、样例、标签和创建者。样例至少包含 `question`、`expectedAnswer`、`type`（`single-hop`、`multi-hop`、`task`、`reject`）、预期证据/拒答条件及租户上下文。
- 数据集必须支持 JSON 导入/导出、严格字段校验、重复样例检测和版本不可变；修改已有数据集时创建新版本，不覆盖历史结果。
- 支持发起、查询、取消（未开始任务）与重跑评测。每次运行记录数据集版本、代码/配置版本标识、开始/结束时间、单例结果、汇总指标与失败原因。
- 评测执行要限制并发和超时；单个样例失败不得中断整批，应记录失败并继续其余样例。

### 4.2 指标与 Ragas 边界

- 在 Java 侧实际计算可由当前证据和期望答案确定的指标，例如命中率、拒答准确率、证据命中率、平均耗时、失败率。说明每个指标的分子、分母和边界。
- Ragas 的 Faithfulness、Context Precision、Context Recall、Answer Relevancy 只有在已配置、已实际调用且返回可验证结果的 Ragas/评测服务时才可标记为“已计算”。
- 若 Ragas 需要独立 Python 服务，建立 `RagasEvaluationPort` 和可配置 HTTP 适配器，并默认关闭；local profile 使用明确标注为“未计算”的实现，绝不能以模拟数值冒充 Ragas 结果。
- 评测中调用 LLM 时，必须记录模型名称、提示词版本/哈希、超时和脱敏后的错误类别，不能记录密钥或完整敏感上下文。

### 4.3 Bad Case 回归闭环

- 将失败、低证据、错误拒答或人工标记的问题沉淀为 Bad Case；记录来源运行、样例快照、失败类别、严重级别、状态、责任说明和时间。
- 对 Bad Case 做去重：基于规范化问题、租户边界、数据集版本和失败类型计算稳定键，避免重复沉淀。
- 提供人工确认“提升为回归样例”、关闭/重新打开、查询筛选和重新运行的 API；任何自动沉淀均不得直接覆盖原始评测数据。
- 回归运行必须能对比基线与当前运行，分别报告修复、回归和不变数量。

## 5. P2-C：指标、仪表盘与审计

- 新增 Micrometer 指标：评测总数/成功/失败、样例耗时、Bad Case 新增/关闭、回归修复/回退、持久化审批待处理/过期/审批结果、入库任务状态。
- 标签只能使用低基数值，例如 `operation`、`result`、`type`、`profile`、`errorCategory`；禁止使用 userId、tenantId、documentId、question、workflowId、traceId 作为指标标签。
- 提供版本化 Grafana Dashboard JSON 与 Prometheus 告警规则示例，覆盖检索错误率、入库死信、审批积压、评测失败率和回归数异常。
- 审计日志记录谁在何时创建/审批/重跑/提升/关闭记录，保留 traceId；日志只包含必要元数据和脱敏摘要。

## 6. P2-D：Docker 真实联调

- 审核并修正现有 `docker-compose.yml`、环境变量、健康检查、依赖顺序与初始化脚本。若 pgvector 与 ParadeDB 无法在同一官方镜像中可靠共存，明确其部署限制并采用可验证的分离方案；不要假设镜像天然包含所需扩展。
- PostgreSQL/pgvector、Redis、RabbitMQ、Neo4j、ParadeDB 都必须提供命名 volume、健康检查和最小权限配置。Grafana 默认密码只通过环境变量传入。
- 若本机 Docker 可用且当前任务允许执行，实际运行 Compose，并完成至少以下真实验证：
  1. 容器健康检查通过，应用 `/actuator/health` 为 `UP`。
  2. 文档首次入库、相同内容重复入库和变更后重建的任务状态正确。
  3. RabbitMQ 消费、Neo4j 关系写入/受限查询、ParadeDB 检索至少各完成一次真实验证。
  4. 创建待审批流程，重启应用后审批并恢复成功。
  5. 执行最小评测集，查询评测结果与 Bad Case；Prometheus/Grafana 可读取相应指标。
- 如果 Docker、镜像下载、网络或凭据受限，仍需完成 Compose 配置校验、可运行测试和文档，但最终必须精确说明未完成的联调步骤与原因。
- 启动 Docker Compose 属于外部环境变更；只有用户明确允许本次启动时才执行。未获授权时只做静态配置检查、代码测试和已运行服务的 HTTP 验证，不得伪造 Neo4j、RabbitMQ、ParadeDB 或 PostgreSQL 的运行结果。
- Docker 验证中必须额外确认聊天响应中的图谱参与状态与实际调用一致：未调用图谱时为 `false`，不能仅因关系图谱页面查询成功就标记聊天使用了图谱。

## 7. API 与测试最低要求

保持现有 API 兼容，并按现有路由风格补充：

- 评测数据集版本的创建、导入/导出、查询。
- 评测运行的触发、状态/结果查询、未开始运行取消、回归对比。
- Bad Case 的查询、提升为回归、关闭/重开。
- 持久化待审批工作流的查询与审批恢复。

至少新增以下自动化测试：

1. 应用重启/重新创建仓储后，未过期待审批状态可恢复；过期、越权、重复审批被拒绝。
2. 同一数据集版本不可变；相同输入重跑的幂等语义符合 API 约定。
3. 评测单例失败不会中断批次；汇总指标分母/分子正确。
4. Ragas 未配置时结果明确为未计算；配置异常不会伪造评分。
5. Bad Case 去重、提升、关闭、回归对比正确，且不跨租户泄漏。
6. 指标标签不包含高基数或敏感字段。
7. 现有 P0/P1 测试、`mvn -q test` 和 `mvn -q package` 继续通过。

可在 Docker 可用时补充 Testcontainers 或真实 Compose 集成测试；不要仅凭 Docker 配置文件或 mock 断言宣称外部服务已联通。
