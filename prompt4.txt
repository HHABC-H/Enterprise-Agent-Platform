## 0. 真实基线与共同约束

### 0.1 开始前必须核对

- `README.md`、`pom.xml`、`docker-compose.yml`、`application*.yml`、现有 Flyway 迁移和全部测试。
- `src/main/java/com/agent/memory`、`infrastructure/memory`、`chat`、`api`、`retrieval`、`ingestion`、`workflow`、`evaluation`。
- `简历.txt`、`记忆prompt.txt`、本文件；若文字描述与当前代码冲突，以代码为基线并在最终报告中列出差异。

当前工作区已有未提交的前端、聊天、入库和多层记忆改动。不得删除、覆盖、回退或格式化无关改动；实现中只能修改本任务直接相关文件。不要执行 Git 提交、推送、重置或启动 Docker Compose，除非用户明确授权。

### 0.2 已核实的记忆模块状态

已有短期记忆、长期记忆、用户画像、会话列表和定时任务的初版代码，聊天链路已传入短期记忆、画像和长期记忆。当前实现尚不满足生产验收：

- `MemoryCompressor` 只是拼接旧消息，不调用 LLM 摘要。
- `StructuredMemoryExtractor` 是正则提取，不能按 JSON 抽取完整画像。
- `SessionSummarizer` 仅扫描 JVM 内的 `activeSessions`，重启/多实例会丢失，并且会重复摘要同一会话。
- 长期记忆目前主要写入 `EPISODIC`，没有用户主动“记住”入口，也没有稳定的 `SEMANTIC`、`PROCEDURAL` 写入策略。
- 清理任务只删除低重要性旧记录，尚未处理冲突、过时标记和摘要幂等。
- Redis 写入存在“读—改—写”竞争风险；真实 Redis、PgVector、embedding、定时任务没有集成验证。

### 0.3 强制工程约束

1. 所有新增注释、Javadoc、日志、错误消息、测试名称、README 均使用中文。
2. 所有记忆读写必须携带 `tenantId`、`userId`、`sessionId`（会话级操作）；身份只能由现有 `IdentityGuard`/Token 解析结果提供，不能信任前端传来的用户身份。
3. 核心领域服务依赖端口；Redis、JDBC、HTTP 模型调用只在 `infrastructure` 适配器中实现。记忆或模型故障不得中断正常聊天，必须降级并记录脱敏 WARN 日志。
4. 密钥、密码、真实 URL、完整对话、长期记忆正文不得写入代码、日志、指标标签或仓库。仅用环境变量和忽略的本地覆盖文件配置。
5. `local` profile 必须无 Redis、PostgreSQL、Neo4j、RabbitMQ、LLM 外部依赖可运行；docker/生产 profile 才启用真实适配器。
6. Mock、内存实现、单元测试、Compose 静态检查、真实服务联调必须在最终报告中严格分层，禁止混为“已完成”。

## 1. P0：完成可靠的多层记忆闭环

P0 完成前，不得将“分布式多层记忆”写为已完成。

### 1.1 短期记忆与压缩

- 保留现有对话 API 兼容性。每次正常回答后原子写入 user/assistant 两条消息；等待审批或生成失败时不得写入虚假的 assistant 回复。
- 保持窗口最多 20 条**消息**、TTL 24 小时和 token 阈值 15000；阈值计算要有明确、可测试的近似规则。压缩后保留最近 5 轮完整对话，并在最前面保留一条 system 摘要。
- 新建 `MemorySummarizationPort`（或语义等价端口）。外部 LLM 适配器在显式启用且已配置时，使用 LangChain4j 生成受长度限制的中文摘要；local profile 使用确定性摘要实现，名称和 README 必须明确它不是 LLM 摘要。
- 压缩不得无限累积旧摘要、不得把 system 摘要当作用户事实，也不得泄露其他用户数据。
- 为 `MemoryStore` 添加原子更新语义。Redis 实现必须避免并发“读—改—写”丢消息（可使用 Lua、WATCH/MULTI 或等价原子方案）；内存实现也要具备等效并发语义。

### 1.2 会话生命周期与定时摘要

- 将会话最近活动时间、关闭状态和最近一次摘要时间持久化到会话存储；不能只使用 JVM `ConcurrentHashMap`。
- 增加兼容现有会话 API 的关闭接口，例如 `POST /api/chat/sessions/{sessionId}/close`。只能关闭当前登录用户的会话；关闭时立刻尝试摘要，失败不妨碍关闭并可由定时任务重试。
- 会话存储增加“查询最近 3 小时活跃且尚未在该窗口摘要”的端口方法；Redis 实现应使用可跨实例读取的索引，不扫描未知 key。定时任务仅处理符合条件的会话，并以摘要窗口/版本实现幂等，避免每 3 小时重复写入同一内容。
- `SessionSummarizer` 用摘要端口生成 200 字以内的 `EPISODIC` 记忆，并在成功后更新摘要水位；摘要来源和时间范围必须保存在长期记忆元数据或等价字段中。

### 1.3 长期记忆、主动记住与过期

- 长期记忆表保留 `tenant_id`、`user_id`、`session_id`、内容、向量、类型、重要性、创建时间；为摘要来源、置信度、有效期、过时状态/替代关系补齐可迁移字段，并提供必要索引。
- 检索必须先在 SQL 中按 `tenant_id` 与 `user_id` 过滤，再取候选并应用 7/30 天时间衰减，最终返回 Top-5。向量服务不可用时返回空结果并降级，不得使用跨用户的文本兜底检索。
- 提供用户主动保存稳定偏好的 API，例如 `POST /api/memories`；身份来自服务端，内容长度受限，类型只允许 `SEMANTIC`、`EPISODIC`、`PROCEDURAL`，重要性须在 0 到 1 之间。重复提交必须幂等或去重。
- 将会话摘要写为 `EPISODIC`；将经规则校验或用户确认的稳定偏好写为 `SEMANTIC`；只有具备明确证据和规则时才写 `PROCEDURAL`，不得由模型无依据推断敏感属性。
- 每日清理：删除超过 30 天且重要性小于 0.5 的记忆；对同一用户同一稳定字段的冲突记忆保留较新且更可靠项，并把旧项标记为过时或替代。若实现 LLM 老化审查，必须默认关闭、可降级且不自动删除高重要性数据。

### 1.4 结构化画像

- 定义严格的画像 JSON DTO：`preferredLanguage`、`codingStyle`、`techStack`、`projectBudget`、`role`、`updatedAt`。验证字段长度、枚举/白名单和值类型，禁止模型直接写 Redis。
- 外部 LLM 启用时，通过结构化抽取端口生成 JSON；服务端负责 JSON 解析、校验、合并和覆盖策略。未启用 LLM 的 local profile 保留确定性提取器，但必须明确降级且不能伪造完整画像。
- 画像 Redis Key 必须按租户和用户隔离；不得因会话关闭或短期记忆过期而丢失。新会话回答时把画像和历史记忆以明确边界拼入 system prompt，且历史记忆不能覆盖证据约束规则。

### 1.5 P0 测试与验收

至少新增并通过：

1. 两个用户或两个租户使用同一 `sessionId` 时完全隔离。
2. 并发追加不会丢失应保留的消息；TTL、20 条窗口、token 压缩、最近 5 轮和 system 摘要均正确。
3. local 摘要降级、LLM 摘要适配器、模型失败降级均可验证。
4. 关闭会话和每 3 小时扫描只生成一次对应窗口的 `EPISODIC` 记忆；应用重建后仍可扫描 Redis 中的活跃会话。
5. PgVector/JDBC 查询参数同时包含 tenant/user 条件；时间衰减、Top-5、过期清理、冲突替代、主动记住均正确。
6. LLM 输出非法 JSON、超长字段、Redis/JDBC/embedding 异常均不会中断聊天。
7. 聊天 Prompt 确实包含当前用户的画像和长期记忆，但不包含其他用户内容。

P0 只能在 `mvn test`、`mvn package` 均通过后报告完成。若未获 Docker 启动授权，Redis/PgVector 只能标记为代码和集成测试覆盖，不能标记为真实服务验证。

## 2. P1：补齐简历中尚未落地的检索、文档与图谱能力

仅在 P0 通过后实施。每一项必须提供开关、local 降级和测试；没有真实外部服务验证时不得写“真实接入完成”。

### 2.1 多格式文档

- 保持 `POST /api/documents/markdown` 不变；新增独立的 multipart 上传接口或受控转换层，不把二进制文件塞入既有 JSON 字段。
- 先支持 PDF、DOCX 和图片 OCR 的可插拔 `DocumentParser`；文件类型、大小、页数/图片数、提取超时、空内容与恶意文件必须受限。
- 未配置 OCR/解析器时返回明确“不支持/未启用”，不得把图片或 PDF 当 Markdown 伪解析。解析后的文本仍必须走现有版本、权限、哈希和幂等入库链路。

### 2.2 真实检索扩展点

- 实现可配置的 Query Rewrite、embedding 和 rerank 适配器；默认 local 保留确定性实现。
- 只有真实调用成功时才可启用 rewrite/rerank 或称为 `text-embedding-v4`、`qwen3-ranker`。失败必须回退到原问题/原排序，并记录低基数错误类别。
- 禁止编造“Hit@5 从 0.60 到 0.80”或“响应降低 40%”等结果；指标只能来自已保存的评测运行。

### 2.3 图谱边界

- 采用固定小型本体和受控 DTO/规则抽取实体关系；LLM 输出只能作为候选，必须经服务端校验、归一化、去重、置信度过滤和来源片段绑定后再写 Neo4j。
- 实现跨文档实体的稳定标识与关系查询，保留租户、权限、文档版本、来源和置信度。不能让 LLM 拼接 Cypher 或直接写图。
- 仅在图证据真实进入回答上下文时才将 `graphEvidenceUsed` 置为 `true`；普通聊天不得暗示 GraphRAG 已启用。
- 如实现短路径缓存，key 必须包含租户、用户权限边界、查询、文档/版本和图数据版本；禁止跨用户复用。

## 3. P2：受控 Agent 与评测闭环

仅在 P0/P1 都有可运行验证后实施。避免为了关键词而制造空的多智能体框架。

- 在现有显式状态机基础上实现受控 Planner/Executor：子目标结构化、依赖校验、最大步数、超时、工具白名单、人工审批和失败回退。只有任务真正可并行且没有共享写冲突时才并行执行。
- Supervisor-Worker 必须是可选能力，保存任务边界、结果去重和最终一致性校验；不因普通聊天请求自动创建多个 Agent。
- 为结构化输出定义 JSON Schema/DTO 校验；校验失败返回重检索、重规划或待审批，不能将模型自评当作真实校验。
- 将评测集扩展到 181 条前，先定义来源、类别分布、版本、人工校验和导入流程；禁止为了凑数复制样例。至少覆盖单跳、多跳、任务、拒答、权限隔离和记忆生命周期。
- Ragas 只有在真实服务调用并保存结果时才标记 `COMPUTED`；未配置时必须保持 `NOT_COMPUTED`。Bad Case 必须能去重、升格为回归、重跑和比较基线。
