## 3. P1 功能要求

### 3.1 父子索引与 Neo4j 关系图谱

- 在现有文档/Chunk 模型基础上补齐父子索引：子 Chunk 用于召回，父 Chunk 用于提供回答上下文。
- 关系模型至少表达：`Document-[:CONTAINS]->ParentChunk-[:CONTAINS]->Chunk`；实体关系可使用 `Chunk-[:RELATES_TO]->Entity`。每个节点和关系必须带租户及文档/版本隔离字段，避免跨租户查询。
- 实现已有或新增的 `GraphRelationSearchPort` 真实 Neo4j 适配器，以及 local profile 可运行的降级实现。图谱能力不可用时，聊天主链路必须继续可用，并明确标记图谱证据未参与。
- 提供受控多跳查询：必须限制起点、最大跳数、返回数量和查询超时；禁止拼接未经校验的 Cypher 片段，避免 Cypher 注入。
- 图谱查询必须在查询条件中执行租户/权限过滤，而不是查询完成后才过滤。
- 若当前项目没有可靠实体抽取模型，先提供确定性、可测试的基础实体抽取策略；不要假称实现了语义实体抽取。

### 3.2 ParadeDB 全文检索适配器

- 实现 `FullTextSearchPort` 的 ParadeDB 适配器，并保留 P0 内存降级实现。
- 将依赖 PostgreSQL/ParadeDB 的 SQL、索引初始化和查询参数放在清晰且可维护的位置；使用参数绑定，禁止把用户问题直接拼接到 SQL。
- 必须保持全文检索与向量检索的结果结构一致，使现有 RRF、权限过滤、重排和证据校验逻辑无需重复实现。
- 对未安装扩展、数据库不可用、索引未构建等情况提供清晰健康状态/降级日志；不得因全文检索失败而绕过权限过滤或返回无证据答案。

### 3.3 RabbitMQ 增量入库

- 实现文档变更事件：事件至少包含 `eventId`、`tenantId`、`documentId`、`version`、`contentHash`、`operation`、`occurredAt` 与 traceId。
- 内容 SHA-256 未变化时不发布重建任务；同一幂等键的重复消息不得重复写入、重复建图或造成旧数据误删。
- 消费流程必须是：读取当前文档版本 → 查询并清理该文档旧索引/图关系 → 切分 → 向量化 → 批量写入检索存储 → 写入图谱 → 标记处理结果。
- 失败处理需具备有限重试、可观测失败记录和死信/人工重试策略；不得无限重试。说明数据库写入与消息确认之间的一致性边界。
- local profile 使用同步、确定性的进程内事件发布器，确保无需 RabbitMQ 也能通过测试；docker profile 使用真实 RabbitMQ 适配器与环境变量配置。

### 3.4 人工审批与工作流检查点

- 在现有状态机中增加明确的人工审批状态（如 `WAITING_APPROVAL`），并定义允许的事件与非法状态转移错误。
- 检查点至少持久化：workflowId、当前状态、输入摘要、待审批动作、创建时间、过期时间、traceId、版本号。不得把完整敏感对话或密钥写入日志。
- 提供恢复 API；审批人身份、审批意见和审批决定必须经过参数校验并记录审计事件。重复审批、过期审批和越权审批必须被拒绝。
- local profile 可以使用可测试的内存检查点仓储；外部存储适配器只在真实依赖可用时启用。

### 3.5 可观测性与文档

- 新增并暴露：增量入库任务数、成功/失败/重试次数、处理耗时、幂等跳过数、图谱查询耗时、审批等待/通过/拒绝次数。
- 所有异步消息、图谱查询与审批恢复必须传播或生成 traceId；不要记录文档正文、模型密钥和敏感审批内容。
- 更新 README：P0/P1 实现矩阵、local/docker profile 的区别、环境变量、数据库初始化、RabbitMQ 交换机/队列、API 示例、回滚/重试说明与验证命令。
- 更新 Docker Compose、Prometheus 配置和必要的初始化 SQL；没有实际运行过的 Compose 部分必须在 README 清楚标为“未实测”。

## 4. API 与测试要求

在尽量保持 P0 API 不变的基础上，提供并记录以下能力的 API（具体路径可按现有路由风格微调）：

- 触发某文档的异步/同步重建，并查询其处理状态。
- 查询指定文档或检索证据的受限图谱关系；请求中必须带租户与用户上下文。
- 查询待审批工作流，提交通过/拒绝决定，并恢复工作流。

必须新增测试，至少覆盖：

1. 子 Chunk 命中后能安全获取对应父 Chunk 上下文。
2. 跨租户、无权限用户、超跳数图谱查询都无法读取受限关系。
3. 相同内容不重复入库；同一事件重复投递只生效一次；失败后有限重试并进入可观察的失败状态。
4. ParadeDB 不可用时正确降级，不绕过权限控制。
5. 审批状态下不能直接完成；批准后可恢复；重复、过期和越权审批被拒绝。
6. 现有 P0 单元测试和 Spring Boot 集成测试仍通过。
